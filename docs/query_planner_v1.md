1. 根因判断是对的：你现在不是“检索不够多”，而是缺少“检索结果驱动下一跳 query”的 agentic loop。相关工作基本都在解决这个问题。

**ReAct** 的核心思想是把 reasoning 和 acting 交替执行，而不是先一次性规划完所有 query。模型每一步先根据当前状态写出下一步推理，再调用 search / lookup 等外部动作，然后根据 observation 更新后续动作。对应你的 case，系统不应该一次性生成 `2018 animated film Cubist influence` 后结束，而应该在检索到 `Night Is Short...` 且 origin=Japan 后触发“constraint conflict”，回到上一跳重新生成更受约束的 query，例如 `2018 European animated film Cubism Picasso Braque`、`Hungarian animated film cubism 2018 box office`。ReAct 的价值就在于把错误检索结果变成下一轮动作的输入，避免单次 query planner 的错误被一路放大。([arXiv][1])

**Self-Ask with Search** 解决的是 compositional question 的拆解问题：模型显式提出 follow-up question，并逐个回答，再合成最终答案。它比普通 CoT 更适合你的任务，因为每个 slot 都可以被写成可验证的子问题，例如“由 Picasso/Braque 共创的运动是什么？”、“哪一部 2018 欧洲动画电影显著受 Cubism 影响？”、“该片全球票房是多少？”。它的不足是仍偏线性，但它给你的启发是：query planner 不应该只输出 query，而应该输出“slot + expected answer type + hard constraints + verification condition”。这样 state3 的 expected answer type 应该是“European animated film, 2018, Cubist influence”，而不是泛化成“2018 animated film Cubist influence”。([arXiv][2])

**IRCoT** 更直接对应你的问题。它指出 multi-step QA 里“该检索什么”依赖“已经推理出什么”，而已经推理出的内容又依赖前面检索到的证据，所以一次 retrieve-and-read 不够；它用 CoT step 和 retrieval 交替推进，让每一步推理生成下一次检索条件。对你的 VDR pipeline 来说，state1 确认 Cubism 后，state2 确认 Picasso/Braque 后，state3 的 query 必须由已有推理链自动收紧，而不是由最初 question 一次性猜出来。也就是说，state3 的 query 应该动态继承 `Cubism + Picasso/Braque + European + 2018 + animated film`，并在检索结果不满足 Europe 约束时继续 refine。([arXiv][3])

**FLARE / Active RAG** 的思想是“主动决定何时检索、检索什么”，尤其是在生成过程中遇到低置信内容时触发新检索，而不是固定检索一次。你的第四次 probe 已经出现了典型触发信号：模型拿到 `Night Is Short, Walk On Girl` 后又发现 origin=Japan，这不是应该中止，而是应该触发 active retrieval，因为当前候选违反了题面约束。FLARE 给你的工程启发是增加 retrieval trigger：当候选实体与 hard constraint 冲突、候选集为空、top result 低相关、或 answer type 不匹配时，系统必须自动生成下一轮 query。([arXiv][4])

**Self-RAG** 强调模型不仅要 retrieve 和 generate，还要 critique 检索材料与自身生成内容；它通过 reflection tokens 控制是否需要检索、证据是否相关、答案是否被支持。放到你的任务里，state3 后面应该有一个 critic：`candidate = Night Is Short`，`constraint European = false`，`support status = contradiction`，所以不能进入 box office 查询，也不能简单拒答，而应该输出 `REFINE_QUERY`。Self-RAG 对你的最大启发是把“矛盾检测”形式化成流程控制信号，而不是让模型自然语言说“证据不足”。([arXiv][5])

**Search-o1** 把 agentic search 嵌入长推理模型：当推理过程中遇到不确定知识点时动态搜索，并用 Reason-in-Documents 模块先分析文档，再把压缩后的有用信息注入推理链，减少检索噪声。你的失败里，问题不是网页完全没有答案，而是搜索结果噪声把模型带到了日本动画。Search-o1 的启发是：retrieval_manager 不应直接把 top-k 网页塞给 reasoner，而应先做 document-level filtering，判断每个网页是否满足 slot 约束，例如 `year=2018`、`region=Europe`、`medium=animated film`、`cubism-related`；不满足的文档只作为 negative evidence，不应污染候选生成。([arXiv][6])

**SmartSearch** 更聚焦 query refinement 本身。它指出很多 search agent 的瓶颈不是最终 reasoning，而是中间 query 质量差；因此用 process reward 指导 query refinement，奖励能带来有效检索和正确中间状态的 query。你的 case 正是这个问题：`2018 animated film Cubist influence` 是低质量 query，因为它没有包含 European、Picasso/Braque、Hungarian/European cinema 等可收缩候选空间的约束。可以借鉴它做一个轻量 query reward：命中候选实体、满足硬约束、带来 candidate set contraction、产生可验证证据的 query 得高分；召回日本动画这种违反约束的 query 得低分。([arXiv][7])

**WebGPT** 的价值在于把 web browsing 设计成可训练、可评估的序列决策任务：模型搜索、打开网页、引用证据，并通过人类反馈优化答案质量。它对你当前 benchmark 的启发不是直接复刻 RLHF，而是把 VDR 的搜索过程也做成可审计 trajectory：每个 query 为什么发出、打开了哪些网页、网页支持/反驳哪个 constraint、为什么继续或停止。你现在的 probe 已经有这种日志雏形，但缺少 policy-level 反馈；后续可以把失败案例转成训练/评估样本，要求 agent 在 `Japan` contradiction 后必须 backtrack，而不是拒答。([arXiv][8])

综合这些论文，我建议你把当前“一次性 query_planner”改成“state-conditioned iterative search agent”。最小改法是保留现有 state pool，但给每个 state 增加四个字段：`constraints`、`expected_answer_type`、`candidate_set`、`failure_signal`。检索流程变成：先按当前 state 生成 query，检索后抽取候选；critic 检查候选是否满足 hard constraints；如果不满足，就把 contradiction 写回 state，并调用 query_refiner 生成下一轮 query。以这道题为例，state3 第一次搜到 `Night Is Short` 后，critic 记录 `origin=Japan != European`，触发 refinement，下一轮 query 必须继承 `Cubism / Picasso Braque / European / 2018 / animated film`，并优先生成实体召回型 query，如 `2018 European animated film Cubism`, `Ruben Brandt Collector Cubism`, `Hungarian animated film Picasso Braque influence`。这样系统的关键变化是：错误结果不再导致中止，而是成为收紧 query 的负证据。

2. 下面这一版可以作为你当前 VDR agentic retrieval module 的“完整设计草案”。核心原则是：benchmark schema 中的 `GT Video State` 只描述视频侧必须被观察到的语义证据；agent 运行时额外维护 `Runtime Retrieval Memory`，用于支持动态检索、候选更新、矛盾检测、query refinement 和后续过程评估。二者必须分离：前者是稳定标注对象，后者是不同模型/agent 可自由探索的执行轨迹。

**1. 统一命名边界：GT Video State 与 Runtime Retrieval Memory 分离。** `GT Video State` 是 benchmark annotation layer，只包含视频理解阶段的必要状态，例如关键时间段、视觉锚点、动作变化、OCR、风格线索、时间关系和视频内可验证的子判断；它不应该包含“应该搜索什么网页”“应该先搜哪个实体”“应该打开哪个网页”这类 agent 行为，因为这些属于执行策略，不同 agent 可以有不同路径。`Runtime Retrieval Memory` 是 agent execution layer，是模型运行时维护的临时工作记忆，包含 `task_hypothesis`、`slot_state`、`candidate_set`、`constraint_ledger`、`failed_constraints` 和 `retrieval_history`。换句话说，GT Video State 规定“视频中必须被理解的事实”，Runtime Retrieval Memory 记录“agent 如何利用这些事实进行开放网页检索和候选消歧”。

**2. 输入总线：Video States + Question + Anchors 共同初始化检索任务。** 整个模块的输入包括原始问题 `question`、视频理解模块输出的 `predicted_video_states`、从视频中抽取的 `visual_anchors`、可搜索实体或属性 `searchable_anchors`，以及可选的 benchmark 标注结构 `GT Video State`，其中 GT 只在评估时使用，不能在实际推理时泄露给 agent。该阶段的输出是一个初始化后的 `Runtime Retrieval Memory`，其中 `task_hypothesis` 存放当前已经从视频中推断出的结构化事实，例如 `{art_movement=Cubism, visual_style=non-objective fragmentation, founders_candidate=[Picasso, Braque]}`；`slot_state` 存放当前待补全的搜索槽位，例如 `target_film_identity`；`candidate_set` 初始为空；`constraint_ledger` 记录题面与视频提供的硬约束，例如 `{year=2018, region=European, medium=animated film, related_to=Cubism}`；`retrieval_history` 为空。这个阶段的目标不是直接生成答案，而是把视频理解结果转成可以驱动搜索的结构化检索状态。

**3. Slot Planner：把开放问题拆成可验证的信息槽位。** `Slot Planner` 的输入是 `question`、`task_hypothesis`、`visual_anchors` 和已有 `constraint_ledger`，输出是一组有顺序但允许回退的 `slot_state`，每个 slot 包含 `slot_name`、`expected_answer_type`、`hard_constraints`、`soft_constraints`、`verification_condition` 和 `dependency`。例如当前案例可以拆成：`slot_1=art_movement`，答案类型是 `art movement`，验证条件是网页或视频证据能支持该视觉风格对应 Cubism；`slot_2=founders`，答案类型是 `person_pair`，约束是与 Cubism 共创相关；`slot_3=target_film_identity`，答案类型是 `European animated feature film`，硬约束是 `year=2018, region=Europe, related_to=Cubism`；`slot_4=box_office_value`，答案类型是 `currency amount`，约束是必须对应 slot_3 中确认的电影。这个模块借鉴 Self-Ask / IRCoT 的问题分解思想，但输出不是自然语言子问题，而是可检索、可验证、可回退的信息槽。

**4. Query Planner：从当前 slot 和 runtime memory 生成候选 query，而不是一次性生成所有 query。** `Query Planner` 的输入是当前 `slot_state`、`task_hypothesis`、`candidate_set`、`failed_constraints` 和最近的 `retrieval_history`，输出不是单个 query，而是一组 `query_candidates`，每个 query 都带有 `intent`、`included_constraints`、`target_answer_type` 和 `fallback_strategy`。例如在 `target_film_identity` 这一跳，合理 query 不应只是 `2018 animated film Cubist influence`，而应生成多个不同粒度的 query，例如实体发现型 `2018 European animated film Cubism`，约束收缩型 `Hungarian animated film Cubism 2018`，关系验证型 `Ruben Brandt Collector Cubism influence`，以及排错型 `European Cubist animated feature film 2018 Picasso Braque`。这个模块的关键变化是：query 必须由当前 runtime memory 动态生成，并且必须显式继承 hard constraints；不能再像现在一样在初始阶段一次性生成全部 query。

**5. Query Utility Estimator：核心版用规则排序，可选版引入学习式 query scorer。** `Query Utility Estimator` 的输入是 `query_candidates` 和当前 `slot_state`，输出是排序后的 query 列表或被选中的 top query。核心版可以使用训练无关的轻量打分，不需要 RL：评分维度包括 query 是否覆盖当前 slot、是否包含关键 hard constraints、是否避开 failed candidates、是否具有候选收缩能力、是否能产生可验证实体、是否过泛或过窄。这里不建议用一个绝对阈值决定所有情况，因为阈值会很 heuristic；更稳的做法是同一轮生成 3–5 个 query，做相对排序，选择 utility 最高的 query 执行。如果最高分也明显缺失关键约束，例如完全没有 `European` 或 `Cubism`，才触发 rewrite。可选增强版可以后续把这个模块替换成 reward model 或 preference model，使它支持 SmartSearch 式 query process reward，但现阶段只需要 test-time ranking。

**6. Retrieval Manager：执行搜索并返回结构化 observation，而不是直接返回网页文本。** `Retrieval Manager` 的输入是选中的 query、当前 slot 的 `expected_answer_type` 和 `verification_condition`，输出是结构化 `retrieval_observation`，其中包括 returned pages、snippet、source type、extracted entities、candidate mentions、answer-type match、constraint evidence 和 source reliability。它不能只把 top-k 网页原文塞给 reasoner，而应先做轻量抽取，例如对于电影身份 slot，要抽取 `film_title`、`year`、`country_or_region`、`medium`、`cubism_relation`；对于 box office slot，要抽取 `gross_value`、`currency`、`source`、`domestic/worldwide`。这样后续模块判断的是结构化证据，而不是一堆噪声网页。这个设计对应 Search-o1 里先读文档再压缩有用证据的思想，但这里被适配成 VDR slot-level document filtering。

**7. Observation Classifier：把检索结果分成 support、contradict、insufficient、type_mismatch、low_relevance、empty_candidate。** 这是你问到的关键点：矛盾检测需要形式化为流程控制信号，但应尽量轻量化。`Observation Classifier` 的输入是 `retrieval_observation`、当前 `slot_state`、`hard_constraints` 和 `candidate_set`，输出是一个控制标签和最小证据说明。`support` 表示 observation 足以支持当前 slot 的候选或假设；`contradict` 表示 observation 明确违反 hard constraints，例如候选电影 origin=Japan 但题面要求 European；`insufficient` 表示 observation 部分相关但证据不完整，例如网页提到某动画受 Cubism 影响，却没有年份或地区信息；`type_mismatch` 表示返回结果类型不对，例如搜电影身份却返回艺术理论课程；`low_relevance` 表示网页语义相关度太低；`empty_candidate` 表示没有形成任何可用候选。这个 classifier 可以用 rule + small LLM hybrid 实现，避免每轮都让大模型生成长篇解释。

**8. 对 insufficient observation 的处理：不应立即回退，也不应直接进入下一跳，而是执行 evidence completion。** `insufficient` 的含义是“当前 observation 没有错，但还不够”。它和 `contradict` 不同，不能直接写入 failed_constraints；它和 `support` 也不同，不能直接进入下一跳。正确动作是触发 `COMPLETE_EVIDENCE`：保留当前 candidate 或 partial clue，把缺失字段转成新的补充 query。例如某网页提到 `Ruben Brandt, Collector` 与 Cubism 有关，但没有明确 box office 或 European origin，那么下一轮 query 应该变成 `Ruben Brandt Collector country 2018 animated film` 或 `Ruben Brandt Collector box office worldwide`，而不是回到泛化 query。也就是说，`insufficient` 的下一步是“补证据”，`contradict` 的下一步是“淘汰或回退”，`low_relevance/type_mismatch/empty_candidate` 的下一步是“重写 query”。这一区分很重要，否则系统会把证据不足误当作错误，导致过度回退。

**9. Memory Updater：把 observation 写回 runtime retrieval memory。** `Memory Updater` 的输入是 observation、classifier label、当前 slot 和当前 memory，输出是更新后的 `Runtime Retrieval Memory`。如果 label 是 `support`，则更新 `candidate_set` 中候选的支持证据和置信度，并把被验证的字段写入 `task_hypothesis`；如果 label 是 `insufficient`，则把候选标记为 `partial_candidate`，记录缺失字段，例如 `missing=[country, box_office]`；如果 label 是 `contradict`，则把冲突写入 `failed_constraints` 和 `constraint_ledger`，例如 `Night Is Short -> origin=Japan conflicts with region=Europe`；如果 label 是 `type_mismatch` 或 `low_relevance`，则只更新 `retrieval_history`，不污染 candidate_set；如果 label 是 `empty_candidate`，则记录该 query 无效，供后续 query planner 避免重复。这个模块是整个系统的“状态更新器”，它保证检索结果不会以自然语言散落在上下文中，而是被结构化地用于下一轮决策。

**10. Control Router：根据 observation label 决定 next hop、evidence completion、query refinement 或 backtracking。** `Control Router` 的输入是当前 `slot_state`、classifier label、更新后的 memory 和预算信息，输出是下一步 action。若 label 为 `support` 且满足当前 slot 的 `verification_condition`，则 action 是 `ADVANCE_SLOT`，进入下一跳；若 label 为 `support` 但 verification condition 仍不完整，则 action 是 `COMPLETE_EVIDENCE`；若 label 为 `insufficient`，默认 action 也是 `COMPLETE_EVIDENCE`，围绕 partial candidate 或缺失字段生成补充 query；若 label 为 `contradict`，action 是 `ELIMINATE_CANDIDATE` 或 `BACKTRACK_AND_REFINE`，具体取决于 candidate 是否还有其他证据支持；若 label 为 `type_mismatch`、`low_relevance` 或 `empty_candidate`，action 是 `REWRITE_QUERY`；若多轮 refinement 后仍无法获得有效候选，才进入 `ABSTAIN_WITH_REASON`。这比现在的“搜不到就拒答”更稳，因为它把失败分成了不同类型，每类失败对应不同动作。

**11. Query Refinement：利用错误结果、partial clue 和 failed constraints 生成更受约束的新 query。** `Query Refinement` 的输入是当前 slot、失败 query、observation label、failed_constraints、partial_candidate 和 retrieval_history，输出是新的 query_candidates。若失败类型是 `contradict`，refinement 要显式排除错误路径，例如 `-Japan` 不一定适合搜索引擎语法，但 planner 的自然语言约束中必须记录“avoid Japanese animation candidates”；若失败类型是 `insufficient`，refinement 要围绕 partial clue 补充缺失字段，例如围绕 `Ruben Brandt` 搜 origin、Cubism relation 或 box office；若失败类型是 `type_mismatch`，refinement 要强化 answer type，例如加入 `film`, `animated feature`, `box office`, `country of origin`；若失败类型是 `empty_candidate`，refinement 要放宽一个非核心 soft constraint，但不能放宽 hard constraints。这个模块是 ReAct/IRCoT 思想在 VDR 里的实际落点：observation 不是终点，而是下一轮 query 的输入。

**12. Verification Gate：只有满足 slot verification condition 才能进入下一跳。** `Verification Gate` 的输入是当前 slot、candidate_set、constraint_ledger 和支持证据，输出是 `verified / partially_verified / rejected`。例如在 `target_film_identity` 中，`Ruben Brandt, Collector` 必须至少满足 `animated film`、`2018`、`European/Hungarian`、`Cubism-related` 这些核心条件，才能进入 `box_office_value` slot；如果只满足其中一部分，则仍是 `partially_verified`，必须继续 evidence completion；如果违反任一 hard constraint，则是 `rejected`。在 `box_office_value` 中，验证条件应检查数值、币种、gross 类型和来源一致性，例如 `$218,184` 是 worldwide 还是 domestic，来源是否可靠。这个 gate 可以防止模型因为看到一个高相关网页就提前跳到最终答案，也能防止错误候选被带入后续票房查询。

**13. Answer Composer：最终答案必须绑定 candidate、video state 和 web evidence。** `Answer Composer` 的输入是已经通过 verification gate 的 final candidate、box office value、对应 web evidence、以及与问题相关的 video state summary，输出是最终答案和可审计 reasoning summary。它不应重新自由发挥，而应只读取 runtime memory 中已验证的字段。例如最终回答应能说明：视频线索指向 Cubism；Cubism 由 Picasso 和 Braque 共创；符合 2018、European、Cubism-inspired animated film 条件的候选被验证为 `Ruben Brandt, Collector`；其票房为 `$218,184`。如果中间某一跳没有通过 verification gate，Answer Composer 应输出结构化 abstention，说明缺在哪个 slot，而不是笼统说“证据不足”。这样最终答案质量依赖前面的验证链，而不是最后一个 LLM 的自由生成能力。

**14. 核心优化模块：建议第一阶段必须实现的最小闭环。** 第一阶段不需要把所有机制都做满，核心优化应包括四个模块：`Runtime Retrieval Memory`、`Slot-conditioned Query Planner`、`Observation Classifier` 和 `Control Router`。这四个模块已经能解决你当前最明显的问题：query 一次性生成、错误候选不回退、insufficient observation 被误处理、矛盾无法触发 refinement。也就是说，最小可行版本是：每个 slot 动态生成 query；每轮 retrieval 后判断 `support / contradict / insufficient / type_mismatch / low_relevance / empty_candidate`；根据标签决定 advance、complete evidence、rewrite 或 backtrack；所有过程写入 retrieval_history。这个版本不需要训练、不需要 RL、不需要复杂 reward model，适合作为 baseline+core improvement 的第一版实验。

**15. 可选优化模块：用于后续提升和消融，不应一开始全部塞入主流程。** 可选优化包括 `Query Utility Estimator`、`Document-level Verifier`、`Constraint Ledger Scoring`、`Multi-query Parallel Search`、`LLM-as-Judge Process Evaluation` 和 `Learning-based Query Reward Model`。这些模块可以逐步添加，用于消融实验。比如先比较 baseline 一次性 query planner 与 iterative planner；再加入 observation classifier；再加入 insufficient evidence completion；再加入 query utility ranking；最后加入 document verifier 或 process judge。这样实验设计会更清楚，能说明每个机制到底解决了哪个失败点。如果一开始全部集成，虽然系统看起来完整，但论文中很难证明是哪一个模块带来了提升，也很难定位失败来源。

**16. 训练可扩展性：当前流程天然支持后续 RL / RLHF，但现阶段不要把它写成 RL 方法。** 这个设计对未来 RL/RLHF 是兼容的，因为它把 agent 的每一步动作、状态、观察、奖励候选都显式记录下来了：`state` 是 runtime retrieval memory，`action` 是 query 或 control decision，`observation` 是 retrieval result 和 classifier label，`trajectory` 是 retrieval_history，`outcome` 是最终答案正确性和过程正确性。后续如果要做 RL，可以把 query selection、refinement decision、candidate elimination decision 作为 action space；把 final answer accuracy、slot verification success、candidate contraction、constraint satisfaction、tool efficiency、避免重复错误候选等作为 reward signals。后续如果要做 RLHF，可以让人工或 LLM judge 对 retrieval trajectory 做 preference 标注，例如比较两个 agent 哪个更早排除了错误候选、哪个 query 更有效、哪个证据链更可信。现阶段你只做 rule/test-time policy，但由于日志结构已经对齐 trajectory learning，后续扩展到 preference optimization 或 process reward learning 会比较自然。

**17. 过程评估设计：retrieval_history 不只是调试日志，也是 benchmark process metric 的基础。** 每次 query、网页、候选、支持/反驳证据、slot 状态变化、refinement 原因都应写入 `retrieval_history`，这会让你后面能评估模型是否真正执行了 VDR 所要求的多跳检索与跨模态约束消歧。可以设计一些过程指标，例如 `valid_query_rate` 衡量 query 是否覆盖当前 slot 和 hard constraints，`constraint_violation_recovery_rate` 衡量遇到矛盾候选后是否能正确回退，`candidate_contraction_rate` 衡量候选集是否逐步收缩，`evidence_completion_success` 衡量 insufficient observation 后是否能补齐缺失字段，`redundant_query_rate` 衡量是否反复搜索同一失败路径。这些指标不是必须第一版全部实现，但 retrieval_history 的结构要提前支持，否则后面很难补。

**18. 推荐消融顺序：从一次性 planner 到完整 agentic retrieval。** 一个清晰的消融可以分成五个版本：`V0` 是当前 baseline，一次性 query planner，没有 runtime memory；`V1` 加入 slot-conditioned iterative query planner，但没有显式 contradiction signal；`V2` 加入 observation classifier 和 control router，能区分 support、contradict、insufficient；`V3` 加入 failed_constraints 和 constraint ledger，支持错误候选驱动的 query refinement；`V4` 加入 query utility estimator，对多个 query candidates 排序；`V5` 加入 document-level verifier 或 LLM-as-judge process evaluation。这样的消融能对应你的失败案例逐步解释：V1 解决一次性规划问题，V2 解决拒答/误跳问题，V3 解决反复掉入错误候选问题，V4 解决 query 过泛问题，V5 解决网页噪声污染问题。

**19. 最终运行流程可以概括为一个闭环。** 系统首先从视频理解模块得到 video-only states 和 anchors，并初始化 runtime retrieval memory；然后 Slot Planner 选择当前需要补全的信息槽；Query Planner 根据当前 slot、task hypothesis、constraints 和历史失败生成多个 query candidates；Query Utility Estimator 选择最有价值的 query；Retrieval Manager 搜索并抽取结构化 observation；Observation Classifier 判断结果是 support、contradict、insufficient、type mismatch、low relevance 还是 empty candidate；Memory Updater 把结果写入 candidate_set、constraint_ledger、failed_constraints 和 retrieval_history；Control Router 决定进入下一跳、补证据、重写 query、回退或拒答；Verification Gate 判断当前 slot 是否满足进入下一跳的条件；最后 Answer Composer 只基于已验证的 video evidence 和 web evidence 输出答案。这个闭环就是你当前 VDR pipeline 需要从 workflow-style retrieval 升级到 agentic retrieval 的核心。

**20. 最重要的设计边界是：benchmark 评估“必须理解什么”，agent 设计“如何去查”。** 你不需要把 IRCoT 的所有 reasoning step 都变成 benchmark state，也不需要把 query planner 的每一步写死进 schema。更合理的论文表述是：we keep benchmark states video-grounded and policy-agnostic, while introducing a runtime retrieval memory for agentic web search. 这样 benchmark 不绑定特定搜索路径，agent 又能借鉴 IRCoT/ReAct/Self-RAG/SmartSearch 的迭代检索思想。你这套方案的核心贡献可以写成：一种面向 Video Deep Research 的 slot-conditioned, constraint-ledger-driven agentic retrieval framework，它用 video-grounded states 初始化搜索约束，用 runtime memory 管理候选、冲突和证据，用 structured control signals 驱动 query refinement，从而解决开放网页检索中候选漂移、错误候选不回退、证据不足误拒答和跨模态约束无法审计的问题。

3. （1）每个字段的含义可以按“视频证据层、运行时记忆层、检索动作层、观测判断层”来理解。`GT Video State` 里的字段描述视频中必须被理解的内容，例如 `state_id` 是视频子状态编号，`time_span` 是该状态对应的视频时间范围，`sub_question` 是视频内需要回答的小问题，`sub_answer` 是视频内答案，`key_evidence_units` 是支持这个状态的关键帧、片段、OCR、物体、动作或视觉风格证据，`evidence_role` 是该证据在推理中的作用。`Runtime Retrieval Memory` 里的 `task_hypothesis` 存当前已经认为成立的结构化事实，例如 `art_movement=Cubism`；`slot_state` 存当前要补全的外部信息槽，例如 `target_film_identity`；`candidate_set` 存当前召回到的候选实体及其支持、反驳、置信度和缺失字段；`constraint_ledger` 存每个候选与每条约束之间的关系，比如满足、违反、未知；`failed_constraints` 存已经明确失败的候选—约束组合，防止反复掉坑；`retrieval_history` 存完整搜索轨迹。`Query Planner` 里的 `slot` 是当前要找什么，`expected_answer_type` 是答案类型，`hard_constraints` 是必须满足的条件，`soft_constraints` 是有帮助但可放宽的条件，`verification_condition` 是什么证据算这一跳完成。`Observation Classifier` 的标签则表示检索结果和当前目标之间的关系：`support` 是支持，`contradict` 是明确冲突，`insufficient` 是相关但不够，`type_mismatch` 是答案类型不对，`low_relevance` 是语义相关度低，`empty_candidate` 是没有形成候选。

（2）“query 显式继承 hard constraints”的意思是，当前检索词不是从原问题自由生成，而是必须把已经确定的关键约束带入搜索动作中，让搜索空间从一开始就被限制在正确区域。比如当前状态已经知道目标必须满足 `year=2018`、`region=Europe`、`medium=animated film`、`related_to=Cubism`，那么 query 不能只写成 `2018 animated film Cubist influence`，因为这个 query 虽然包含年份和风格，但没有显式继承 `European` 这个硬约束，也没有利用 `Cubism` 的上游来源信息，所以容易召回日本动画、美国动画或普通风格评论。更合理的 query 应该是 `2018 European animated film Cubism`、`Hungarian animated film Cubism 2018`、`European Cubist animated feature film 2018`。这里的“继承”不是说每个 query 必须机械包含所有字段，而是说 query planner 在生成和选择 query 时必须检查：这个 query 是否服务于当前 slot，是否覆盖必要 hard constraints，是否避免已经失败的候选方向，是否能收缩候选空间。如果 query 没有继承关键约束，它就不是一个合格的 agentic query，而只是普通搜索词。

（3）`contradict` 的下一步我说成“淘汰或回退”，不是说它不需要重写 query，而是说重写 query 之前必须先处理冲突的对象，否则会变成盲目改 query。`contradict` 表示已经有明确证据证明某个候选或某条假设违反硬约束，例如 `Night Is Short` 的 origin 是 Japan，而当前 hard constraint 是 European；这时第一步应该是把这个候选写入 `failed_constraints` 或从 `candidate_set` 中降权/淘汰，也就是先更新 memory。之后通常会进入 query refinement，但这个 refinement 是“带着冲突记忆的重写”，不是普通重写。区别在于，`type_mismatch`、`low_relevance`、`empty_candidate` 的重写主要是因为 query 本身不够好；而 `contradict` 的重写是因为某个候选被证据否定了，系统需要先记录“为什么错”，再生成能避开这个错误方向的新 query。所以更精确的说法应该是：`contradict -> update failed_constraints / eliminate or revise candidate -> backtrack if needed -> constraint-aware query refinement`。它当然包含重写，但重写不是第一语义动作，第一语义动作是冲突吸收和候选处理。

（4）当前设计看起来像 workflow，是因为我们把模块边界、输入输出和控制信号写得很清楚，但这不等于它不是 agentic。`workflow` 更像固定流程：先做 A，再做 B，再做 C，每个样本都按同一路径执行，失败后没有自适应决策；而这里的 agentic 特征在于，系统会根据 observation 动态决定下一步是进入下一跳、补证据、淘汰候选、回退、重写 query，还是暂时保留冲突继续搜索。也就是说，外层有一个清晰的工程框架，但内部 action 是条件化和状态驱动的。ReAct、IRCoT、Self-RAG 这类方法本身也不是完全无结构的自由探索，它们都有“reason/retrieve/observe/update”的循环，只是决策点由模型或策略控制。你的设计可以被表述为 structured agentic workflow，或者 agentic retrieval controller：它不是纯自由 agent，但也不是固定 workflow；它是把 agent 的动态决策限制在可审计、可评估的状态转移空间里。对 benchmark 来说，这反而是优点，因为完全自由的 agent trajectory 很难评估，也很难复现。

（5）字段确实不能无限复杂化，参考论文里通常不会把工程字段展开得这么细，因为论文方法往往只描述核心抽象，例如 ReAct 只讲 reasoning/action/observation，IRCoT 只讲 interleaving retrieval with CoT，Self-RAG 只讲 reflection/control tokens，SmartSearch 只讲 query quality and refinement；它们不会在主文里列一堆生产级字段。你现在的设计偏工程化，但不一定是坏事，因为 VDR 任务比普通文本 QA 多了视频状态、视觉锚点、网页证据、候选消歧和跨模态冲突，字段多是由任务复杂性决定的。论文写作时不要把所有字段都当作 idea，而应把 idea 抽象成三件事：video-grounded states 与 runtime retrieval memory 解耦；slot-conditioned retrieval；constraint-ledger-driven refinement。具体字段只是实现这个 idea 的 schema，可以放在方法细节、附录或实现部分。最小核心字段其实只需要 `slot_state`、`task_hypothesis`、`candidate_set`、`constraint_ledger`、`retrieval_history`；其他字段如 `query_utility_score`、`source_reliability`、`soft_constraints`、`missing_fields` 都可以作为可选扩展。这样论文不会显得只是堆工程，而是有清晰方法抽象。

（6）目前设计已经在框架上解决了“搜索结果的新信息和背景信息冲突时怎么处理”的问题，但还需要把冲突类型分清楚。第一类是新信息和视频证据冲突，这时应以视频信息作为 gold version，尤其是在 benchmark 设定里，视频是任务输入的核心证据，网页只能帮助识别、扩展和验证，不能推翻视频中明确可见的事实；例如视频中明显是石狮子，网页或模型说是老虎，应该记录为 `web/text conflict with video anchor`，并降低该候选或网页证据权重。第二类是新信息和题面文本冲突，原则上 benchmark 构造阶段应尽量避免这种问题，因为题面是任务约束来源；如果真实运行中出现“题面说老虎但视频看起来是石狮子”，系统不应擅自改题，而应标记为 `question-video inconsistency`，在 benchmark 中这类样本最好剔除或单独作为鲁棒性测试，不应纳入主评测。第三类是新信息和之前搜索信息冲突，这不能简单丢弃新信息，也不能立刻覆盖旧信息，而应进入 `conflict_pending` 状态：保留两个版本，记录各自来源、时间、可信度、是否满足当前 slot、是否与视频/题面 hard constraints 一致，然后触发 targeted verification query。比如一个网页说电影票房是 `$218,184`，另一个说不同数字，系统应继续搜索 BoxOfficeMojo、The Numbers、IMDb、Wikipedia 等更结构化来源，并明确 gross type 和币种，而不是直接采用最新网页。也就是说，冲突处理的总原则是：和视频冲突时优先视频，和题面冲突时标记样本/问题异常，和搜索证据冲突时暂存并追加验证，直到有足够来源或权威来源支持某一版本。

关于“怎么高效检测冲突”，可以先不要做复杂 NLI，而采用分层检测：结构化字段冲突用规则最快，比如年份、国家、金额、实体名、类型可以直接比对；同义或细粒度语义冲突用 embedding 或小模型判断，比如 “European” 与 “Hungarian” 是兼容，不是冲突；复杂描述冲突再交给 LLM judge，比如“受 Cubism 影响”是否被网页真正支持。这样不会让每一轮都变成重型推理。冲突检测的关键不是追求一次判得绝对正确，而是把明显冲突尽快拦住，把不确定冲突标记为 `insufficient` 或 `conflict_pending`，再通过 targeted verification 解决。这个机制正好补上你当前系统的漏洞：以前新信息一旦进入搜索链路，就可能污染后续推理；现在新信息必须先经过 constraint check 和 memory update，才能决定是吸收、暂存、淘汰还是触发 refinement。
